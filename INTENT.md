The goal here is to build an optimization program for Python projects that uses an LLM to generate candidates, then applies genetic optimization to combine the best-performing ones. Since code optimization is a hard problem to solve, it’s hard to find the most optimized program for a general project; we propose a greedy solution that finds the best possible case at each block in the program. For this use case, we can leverage Python’s AST package to derive a graph of blocks in the project to optimize the program. The limitation here is that any project submitted must include Python tests and benchmarks we can use to test and evaluate candidates. These tests should be encompassing enough that we would know if candidates are breaking. Benchmarks might include runtime checks or complexity checks. These should not be pass/fail and should be run at the very end to ensure changes are in the right direction.

The entry point here is main.py, which also functions as an orchestrator for the other components in the project. The program will start by identifying the intended configuration for this project; this could be defined by user input or by general hard-coded functions they choose to use. The config file will also store a mapping of test functions we can use to evaluate candidates. Next, the program will run a loader that discovers files, finds entry points, and builds an import graph. These mappers help the program determine connections between files and functions that must be protected. In addition, the mappers help establish connections to libraries outside of the project. After that, the program determines the project's intent, which is stored for the agent to keep; for now, this is done by reading the documentation. Then the analyzer will convert the files into AST trees, create a searchable index, determine which functions call other functions, and score the current code based on predetermined parameters. The analyzer will also determine where to start, usually by picking the most complex or slowest-running option and working up from there. The optimization loop consists of a context builder that stores the necessary information for the agent and passes candidates back to a mutation generator. Initially, candidates are evaluated on a pass/fail basis, and then they are combined. Since candidates can vary in their intended optimization paths, mutations might not be the best suited, which is why we will rerun tests to ensure they still pass. We would evaluate on standalone tests as well as fuzz-generated tests to ensure we catch false positives and false negatives before reaching the codebase. Finally, we would run benchmarks and could rely on other libraries, such as Ruff, to assess complexity. We score mutations across generations and place them back in the codebase. We can repeat this across the project, greedily changing blocks within functions, until we get to the end. At the end, we would generate a report, assuming that if every part of the code is slightly optimized, the codebase would be more optimized as well.
